# Aqours agent guidance

## Project and stack

Aqours is a water supply reporting and customer assistance system connecting a water supplier with its customers. Customers report outages, low pressure, leaks, and water-quality concerns. The supplier views reports and affected areas on a Leaflet map, manages incidents, and provides updates. Native customer map previews use the existing MapLibre integration.

Use TypeScript for application code in all three projects:

| Directory     | Responsibility                 | Stack                                     |
| ------------- | ------------------------------ | ----------------------------------------- |
| `aqours-api/` | Backend and authorization      | Express                                   |
| `aqours-app/` | Customer mobile application    | React Native with the existing Expo setup |
| `aqours-web/` | Water supplier web application | React                                     |

The intended database is containerized PostgreSQL. This stack describes the intended system, not a claim that every component is already implemented.

## Read before working

1. Read root `PROGRESS.md` first to learn what is already built. If it is missing, inspect the repository and initialize it with verified facts before implementation.
2. Read the reference documents relevant to the task:

   | Document               | What to look for                                             |
   | ---------------------- | ------------------------------------------------------------ |
   | `docs/architecture.md` | System design, component boundaries, and data flow           |
   | `docs/requirements.md` | Required behavior, user roles, and access permissions        |
   | `docs/schema.md`       | Database entities, relationships, and constraints            |
   | `docs/workspace.md`    | Local setup, workspace conventions, and development commands |

   These four documents are planned and were absent when this guidance was created. Check whether they now exist; do not invent their contents or treat missing documentation as evidence that functionality exists. Resolve missing requirements that materially affect the task before implementing them.

3. Read applicable directory-specific `AGENTS.md` files before working in those directories. Preserve the existing mobile guidance in `aqours-app/AGENTS.md`. Its technical installation instructions do not grant permission to add dependencies.
4. After implementing each feature, identify and update all relevant documentation to reflect the implemented behavior, structure, setup, and limitations. Verify that the documentation matches the final changes before marking the feature complete.

## Scope, dependencies, and permissions

- Touch only files relevant to the requested task and preserve unrelated work.
- Do not introduce new frameworks or libraries without explicit user approval. The intended stack above does not by itself authorize dependency installation.
- Respect each user's role and access boundaries. Enforce authorization in the backend, including access to individual records; UI restrictions alone are insufficient. Consult requirements before defining additional roles or permissions.
- Keep all changes within this project directory. This includes files generated by commands, caches, configuration, and installation tools. Check command side effects and configure project-local output locations where necessary.
- Do not modify external files, system settings, or the developer's environment without explicit consent for that exception. If a task requires such an action, explain the exact command and expected effects and obtain consent before proceeding. This includes `sudo`, global installations, and commands requiring elevated permissions. Permission to work on the project is not consent to change the surrounding filesystem.
- Treat .env files and secret-bearing environment variables as sensitive: do not read, print, log, copy, commit, expose, or change their values; use placeholders in examples and update only .env.example when documenting configuration.

## Modularity and file limits

Each file must have one focused responsibility. Split features into cohesive modules instead of putting an entire feature or multiple unrelated features into one file. Separate screens, reusable UI, hooks, request handling, business logic, and database access as appropriate to the project.

Hard limits for handwritten TypeScript and TSX files:

| Project                      | Maximum lines per file |
| ---------------------------- | ---------------------: |
| React Native (`aqours-app/`) |                    300 |
| React web (`aqours-web/`)    |                    250 |
| Express (`aqours-api/`)      |                    200 |

Count every physical line, including imports, comments, and blank lines. These limits include tests but exclude generated files, dependencies, and lockfiles. Split by responsibility before exceeding a limit. Do not compress formatting or remove useful documentation to evade it. Bring existing oversized files within the limit when materially changing them; avoid unrelated cleanup.

## Git workflow

- Inspect the branch and working tree before making changes. Preserve existing staged and unstaged changes; do not reset, discard, or include unrelated work in a commit.
- Before implementing a new feature, create a descriptive `feature/<name>` branch, such as `feature/admin-dashboard`. Continue on that feature branch for subsequent work on the same feature.
- When committing, use a concise subject and a detailed body explaining what changed, why it changed, and how it was verified. Mention material limitations or checks that could not run.
- After implementing and verifying a feature, create at least one commit containing all changes for that feature on its feature/<name> branch. Do not include unrelated changes or mark the feature complete until the commit succeeds.

## Verification and progress log

- Run the relevant available checks for the changed components before declaring work complete, following their local guidance and documented commands. Report checks that could not run and why. Documentation-only changes require a content and diff review rather than application tests.
- After completing work, update root `PROGRESS.md` with a short `YYYY-MM-DD` summary of what changed and how it was verified. Record completed work and current limitations accurately; do not describe planned functionality as implemented.
- Keep the log readable and formatted. Count all physical lines, including headings and blank lines.
- If `PROGRESS.md` exceeds 150 lines, archive the complete log to `docs/logs/PROGRESS-YYYY-MM-DD`, using the date of archival and creating the directory if necessary. Start a fresh root `PROGRESS.md` with a link to the archive and a brief current-state summary.
- Never overwrite an archive. For multiple archives on the same date, use the next available numeric suffix, such as `PROGRESS-YYYY-MM-DD-2`.
